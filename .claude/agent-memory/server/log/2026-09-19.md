
## Dev server down: TDZ crash on every index.get.ts route + eventually SSR itself

Reported symptom: `Cannot access 'index_get$N' before initialization` on
`/api/forge-json-compiler`, `/api/forge-script`, `/api/keywords`, plus (found
during investigation) `/api/sink-catalog`, `/api/recognizers`,
`/api/sink-derivations`; `/api/docs` and `/api/engine-status` unaffected.
Reproduced on the shared dev server and confirmed NOT a stale-`.nuxt`-cache
issue (persisted through a clean rebuild).

Bisected via a disposable `git worktree` at HEAD (rsync'd working-tree
subtrees in incrementally — `git stash` is blocked by this environment's
sandbox as destructive) rather than touching the real working tree. Root
cause: `functional-model/scripts/experiments/forge-json-compiler/
load-token-scripts.ts` (new, untracked file from today's schema-agent work)
computed `REPO_ROOT` via `resolve(import.meta.dirname, ...)` at module top
level; Nitro's dev bundler flattens the whole server tree into one
top-to-bottom-evaluated file, and `import.meta.dirname` resolves to
`undefined` there, throwing uncaught during that one-time evaluation —
killing initialization of every route/const positioned later in the
flattened bundle (which is why the failing set looked arbitrary and why the
error later escalated to the SSR `renderer` itself going down too, once the
orchestrator's own `.nuxt` rebuild attempt overlapped with my kill of the
real dev server mid-bisection — apologies for that overlap, restored
immediately after).

Fix: replaced the `import.meta.dirname`-relative path with a
`process.cwd()`-relative one (matches this codebase's established dev-util
convention). Verified fix first in the disposable worktree, then applied to
the real file and restarted the real dev server (port 3000) — confirmed
`/`, `/api/keywords`, `/api/docs`, `/api/sink-catalog`, `/api/recognizers`,
`/api/sink-derivations`, `/api/forge-json-compiler`, `/api/forge-script`,
`/api/card/fdn/1` all 200 with real (non-empty, correct-shaped) bodies.
Left the two sibling files in the same experiment dir that also use
`import.meta.dirname` (`run-experiment.ts`, `fdn-1-50.test.ts`) untouched —
standalone `vite-node`/vitest entry points, never reached by any
`server/api/**` route, not part of the Nitro bundle.

Deploy/CI state: no other changes since last recorded state
(`netlify.toml`'s Node-version pin, review-panel config retirement) —
production build/Netlify plumbing untouched by this fix; this was purely a
local-dev-server issue (Nitro's dev bundler behavior, not present in a
production Netlify Function build in the same way, though the same
`import.meta.dirname`-at-top-level pattern would be worth a sweep before
this experiment dir is ever wired into a prod path).
