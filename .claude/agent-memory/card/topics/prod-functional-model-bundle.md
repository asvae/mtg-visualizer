# Production serves functional-model data from a committed static bundle

Netlify Functions ship only what Nitro/Rollup can statically trace as
imports. Raw `functional-model/` fs reads, dynamic `import()` of a card's
`definition.ts`, and spawning `vite-node` as a subprocess (the dev-only
live-recompute path — see `topics/nitro-mjs-import-gotcha.md`) are all
absent from the deployed bundle. `server/api/card/[set]/[number].ts` and
`server/utils/functionalModelPool.ts` both branch on `NODE_ENV ===
'production'` and, in prod, read from a **committed static JSON import**
instead of touching the filesystem at request time:

- `scripts/build-fm-bundle.mjs` (`npm run sync:fm-bundle`, runs under
  `vite-node`) walks every `functional-model/cards/<slug>/`, executes
  `definition.ts` once, and writes one file: `data/functional-model/
  fm-bundle.json` — carries a hand-picked `CardDefinition` field subset
  (only what `synergy.ts`'s matcher and the served shape actually need),
  plus `synergy.json`/`trace.json`/`progress.json` content and various
  additive per-card fields added over time (`continuousKeywordGrants`,
  `reviewSnapshotAt`, `cardStatus`, `reviewCaveat`, ...).
- `server/utils/fmBundle.ts` does a plain static `import` of that JSON
  (proven to survive Rollup's static trace, same pattern
  `data/global_relations.json`/`data/fin/fin_relations.json` already use)
  and exports it typed as `Record<string, FmBundleEntry>`.
- The dev branch of every affected route is unchanged — always the live
  recompute path, freshest on every edit.
- Similarly, `data/fin/fin_card_status.json` (the whole-pool card-status
  dashboard batch file) is a real prod fallback source, generated by
  `npm run card-status`.

**Staleness contract, deliberate**: `fm-bundle.json` (and
`fin_card_status.json`) are committed but NOT regenerated automatically by
`npm run build` or any CI step — regenerate via the script and commit the
diff by hand whenever `functional-model/cards/` content changes. Every new
field added to the bundle inherits this same "stale in prod until manually
re-synced + committed" contract; a card agent adding a new served field
must thread it through `FmBundleEntry`/`build-fm-bundle.mjs` for prod
completeness, but does NOT need to actually run the regen+commit as part
of a routine task if the working tree already has a large amount of
unrelated in-flight `functional-model/` changes (regenerating would sweep
all of that into the bundle diff too) — leaving it stale until a dedicated
regen pass is an accepted, standing tradeoff, not a bug to fix inline.

`definition.ts`'s dynamic import has no clean Lambda-compatible equivalent
at all (raw TS source, not a bundle-traceable import) — this static-bundle
design is the resolution to that, not a workaround pending a "real" fix.
