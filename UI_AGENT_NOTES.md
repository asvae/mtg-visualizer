# UI/frontend agent notes

Handoff doc for whoever picks up frontend/architecture work on this project next.
Written at the end of a long session that acted as the "UI agent" — running
alongside a separate "reviewer" session that owns card tagging content
(`scripts/REVIEW_PROCESS.md`, `scripts/TAGGING_RULES.md` / `GLOBAL_TAGGING_RULES.md`,
`data/**/*_relations.json`). This doc is the UI side's memory; it doesn't attempt
to explain the tagging/data-pipeline side in depth — read that session's own docs
for that.

## Scope split (as established this session)

- **UI agent** (this doc's author): Vue components, `src/store.ts`, `src/lib/`,
  `vite.config.js`, the landing page, build tooling, `review-server.mjs`/
  `review-relay.mjs`/`ReviewSession.vue` (the review *panel*, as opposed to its
  *content*).
- **Reviewer agent**: authors `data/<set>/<set>_relations.json` content and the
  tagging-rules docs. Runs the live review loop against the panel this session
  built. Coordinate via cross-session `SendMessage` whenever a change affects
  the other side (e.g. a data-path rename, a protocol/schema change) — this
  came up repeatedly and worked well as a pattern; keep doing it.

## Architecture (current, as of this doc)

- **No build-time graph artifact.** `src/lib/buildGraph.ts` assembles the
  `GraphFile` (cards + themes + edges) *client-side*, at load, from raw fetched
  pieces. There is no `fin_graph.json` or equivalent — this was a deliberate
  choice ("graph should be generated by visualizer, not in advance by some
  server script").
- **Two-page site.** `/` is a static landing page (`index.html` + `src/landing.css`,
  no Vue) listing the FIN set's 10 official draft archetypes with links into
  `/app/?colors=...&themes=...`. `/app/` (`app/index.html` → `src/main.ts`) is
  the actual Vue graph visualizer. `vite.config.js` has
  `build.rollupOptions.input` listing both entries explicitly — don't remove
  that or the production build silently drops one page.
- **`src/store.ts`** — single reactive store, provide/inject, no Pinia. Owns:
  - Attribute filters (colors/rarities/types) + theme checklist (`selectedThemes`).
  - Two click-to-highlight selections: `themeSelection` (click a theme node)
    and `cardSelection` (click a card node — new this session). Both behave
    identically in the graph's highlight/dim pass (`refreshHighlight` in
    `graphRenderer.ts`): the clicked thing shows full connectivity, dimming
    everything unrelated.
  - **Two-way URL query sync**: filters + `themeSelection` (`focus=`) +
    `cardSelection` (`card=`) all read from and write to the URL
    (`history.replaceState`, not `pushState`). **Deliberately excludes
    `searchQuery`** — search stays `localStorage`-only, per explicit
    instruction ("that should not connect to search"). See `updateUrlParams`/
    `readUrlParam` in store.ts. Watch out if you touch this: there was a real
    bug (fixed) where `knownThemeIds` got set to the URL's own theme list
    instead of *every* current theme id, which made every non-listed theme
    look "unknown" and default back on — silently ignoring the URL. If theme
    filtering-from-URL ever seems to not apply, check that logic first.
  - Default/reset theme selection is **strong themes only** now (not literally
    every theme) — `selectDefaultThemes()`, using `computeWeakThemeIds` from
    `lib/filters.ts`. The checklist's own "All"/"Strong" buttons
    (`ChecklistSection.vue`) are separate, unaffected, still do what they say.
  - `VITE_ENABLE_REVIEW` env var gates the review panel (button in
    `AppHeader.vue`, `<ReviewSession>` in `App.vue`) — unset on a public
    deployment, set to `1` in local `.env` (gitignored; `.env.example` is the
    committed template).
- **`src/lib/graphRenderer.ts`** — imperative D3 force simulation, persistent
  node objects. Notable recent changes:
  - A card tied to the same theme via >1 edge always renders that link dashed,
    regardless of role.
  - Clicking a theme (or a card) only highlights edges actually touching the
    clicked thing — NOT every edge of every card that happens to touch it (this
    was a deliberate reversal of the original "show full card connectivity"
    design; see `cardIdsFromCardMatch` vs `cardIdsFromThemeMatch` in
    `refreshHighlight`).
  - Initial zoom is 0.35 (`INITIAL_ZOOM` const), not 1.0 — the force layout
    spreads well past one screen, so 100% used to just show whatever settled
    near the top-left.
- **Card node click**: plain click → select (highlight themes, URL-bound).
  Ctrl/Cmd-click → open Scryfall in a new tab instead (`card.scryfallUri`).
  Wired in `GraphCanvas.vue`'s `onCardClick` handler.
- **`src/components/CardLookup.vue` was removed** (dead/unused feature, per
  explicit instruction) along with `store.lookupOpen`. `store.lookupHighlightCardId`
  survived — `ReviewSession.vue` still uses that exact mechanism to highlight
  the card currently under review.

## ⚠️ Known gap: multi-set migration is IN PROGRESS, by another agent, right now

Cross-reference: `scripts/HISTORICAL_SETS_PROCESS.md` is that session's own
handoff doc for the historical-sets/multi-set tagging project — read it first
for anything in this section, it'll have far more detail and be more current.

While this doc was being written, another session was actively editing files
this session owns (`src/lib/buildGraph.ts`, `src/store.ts`, `scripts/prefill-main-types.mjs`,
`scripts/derive-type-themes.mjs`) to migrate from the single-set `data/themes.json`
to a new global, set-agnostic `data/global_themes.json` (+ `data/global_relations.json`,
`scripts/GLOBAL_TAGGING_RULES.md`, and real historical-set data directories
`data/lea/`, `data/leb/`, `data/arn/`). **Don't assume this doc's description of
those files is still current — re-read them before touching.** What was true
at the moment this doc was written:

- `src/store.ts` already fetches `/global_themes.json` (not `/themes.json`
  anymore) — but `const SET_CODE = 'fin'` is still hardcoded, so this is a
  partial migration: the theme *source* moved, but there's still no
  set-selector UI and no code path reading `lea`/`leb`/`arn` or
  `data/global_relations.json` at all. `npm run typecheck` still passed at
  this point, so the partial state isn't broken, just incomplete.
- The landing page is still FIN-specific (its 10 archetype cards are FIN
  draft archetypes) with no "pick a set" concept.
- Before continuing this migration or building a set-selector, read
  `scripts/GLOBAL_TAGGING_RULES.md` and check for whatever process doc exists
  for the multi-set pipeline (don't assume none exists) to understand the
  actual intended data shape — don't guess from file names alone. In
  particular, work out whether "themes" are meant to be global across every
  set simultaneously (one unified graph?) or per-set-selected (pick a set,
  see that set's graph) — the layout (`global_themes.json` shared, but
  relations still split per set-code directory) suggests the latter, but
  confirm before assuming, ideally by asking whoever's driving this rather
  than inferring from partial in-flight edits.
- `data/default-cards-20260830090538.jsonl.gz` and
  `data/oracle-cards-20260830090156.jsonl.gz` are raw Scryfall bulk-data dumps
  (78MB/24MB) sitting in `data/` — almost certainly a `fetch:set`-equivalent
  intermediate for the multi-set pipeline, not something the app itself should
  ever fetch/serve as-is. Don't wire these into `vite.config.js`'s `publicDir`
  assumptions without checking they're meant to be public-servable.

**Confirmed real bug, not fixed yet** (flagged directly by the session doing
the migration, right before it also wrapped up): `vite.config.js` has
`publicDir: 'data'`, which ships the ENTIRE `data/` directory as public static
assets on `npm run build` — no filtering. That directory now also holds the
two multi-gigabyte-adjacent bulk Scryfall exports above plus a growing
`data/global_relations.json`, none of which should end up in a production
bundle. Needs an actual fix: either move the app's real runtime assets
(`*_scryfall.json`, `*_relations.json`, `*_tokens_scryfall.json`,
`global_themes.json`, `type_themes.json`) into a dedicated public subfolder
separate from whatever staging/bulk files the tagging pipeline accumulates in
`data/`, or write a small custom Vite plugin/build step that copies only the
specific files the app actually fetches instead of using bare `publicDir`.
Don't ship a `vite build` to production until this is addressed — it will
currently bundle 100+MB of irrelevant data.

## Dev workflow reminders

- Restart pattern used throughout this session:
  ```
  lsof -ti:5173 -sTCP:LISTEN | xargs -r kill
  nohup npm run dev -- --host > /tmp/vite.log 2>&1 & disown
  ```
  (`--host` binds `0.0.0.0`, needed since the user exposed the dev server to
  their LAN at one point — harmless to keep by default.)
- `usePolling: true` in `vite.config.js`'s watch config is required — this repo
  lives on a WSL2 `/mnt/c` NTFS mount, and inotify doesn't fire reliably there.
- Always run `npm run typecheck` (vue-tsc) after any `.vue`/`.ts` edit — this
  session caught several real bugs that way (e.g. a missing `src/vite-env.d.ts`
  broke `import.meta.env` typing when the env-gate feature was added).
- `npm run build` actually emits both HTML entries now — verify with it
  (not just `typecheck`) after touching `vite.config.js` or either `index.html`.
- The user's session runs a `SessionStart` hook that puts responses in a very
  terse "caveman mode" register (drop articles/filler, fragments OK, but code/
  commits/security callouts stay in normal prose) — if that's still active,
  match it; if not, ask rather than assume either way.
